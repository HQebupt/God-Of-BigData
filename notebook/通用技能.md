# 线上问题定责原则

**总原则：故障处理链路上所有未达成自己职责的各方均需要对故障的时长负责**

目的：双方对过程和查清楚的事实认定清楚。定责的原则是看看哪些地方没做好，促进各方了解并尽到自己的工作职责，做好稳定性。

判定职责的原则是什么
* 故障根因
	- 卡这么久：topic消费方未关注消息积压，因为有积压不一定是因为mq或者flink的问题导致的
	- 恢复的慢：1. 对MQ保存时间双方都有误判 2. 达到当前机制下的消费瓶颈，第一次出现排查时间久

* 责任划分
	- 原则：没做好的各方都需要负责，但延迟或卡住可以不是事故，之所以拖成了事故造成消息丢失，topic消费方没关注积压报警负主责，分责 >= 51%
	- 诉求：我们不负主责，因此不接受55分这种和稀泥的分法

* 对后续的影响
	- 事故责任划分清楚之后，其实是利好长远合作，督促我们以后及时发现、定位根因



## 划分比例
定责是事故复盘中关键的一环，需要明确事故触发的直接原因、间接原因、各方稳定性工作职责等多方面导致事故发生和影响面扩大的问题，并划分责任比例。

定责原则：需分摊责任的责任干系方范围，从以下方面考量：
* 事故发生的直接原因，是在时间上最接近事故发生的原因，包括人的原因、物的原因、环境原因，例如误操作、代码bug等。
* 事故发生的间接原因，是引起事故的原因，包括技术原因、管理原因、社会原因。
* 导致事故影响面扩大的原因，是在事故发生之后的环节中由于人、工具、流程等原因导致事故未尽快恢复，包括感知、响应、定位、止损、恢复各阶段中的平台工具的效率，以及人员决策、执行的效率。

## 场景举例

**场景1：服务提供方异常**

a）场景描述：服务提供方出现故障，导致服务调用方也出现故障，调用方无法降级；

- 定责标准：
  - 服务提供方承担从故障开始到自身服务恢复后1分钟内的故障时长；
  - 如果服务调用方可以在1分钟内恢复服务，则不承担任何责任；
  - 如果服务调用方不能在1分钟内恢复服务，则1分钟后的时间为调用方承担责任；
- 原则：线上服务在稳定性保障上需要有快速自恢复的能力，不能异常后无法恢复或恢复时间过长；
- 更详细定责方案参看：http://wiki.intra.xiaojukeji.com/pages/viewpage.action?pageId=36620655



b）场景描述：服务提供方出现故障，导致服务调用方也出现故障，调用方可降级；

- 定责标准：
  - 降级操作是上下游之前已明确的预案，上下游确定执行预案后，*5分钟内*调用方完成降级则调用方无责，*5分钟*后的时间调用方和服务提供方*平分责任*；
  - 降级操作是上下游临时确定的方案，则服务提供方承担所有故障时长；
- 原则：保障重要预案的有效性是调用方服务运行的一部分；服务提供方接入调用方服务时应对降级预案进行准入*或提前向接入用户发布过相关的申明*；



c）场景描述：调用方对服务提供方强依赖，但实际可以做成弱依赖；

- 定责标准：
  - **服务提供方未向服务调用方提出过弱依赖改造需求**，则首次出现服务提供方引起的故障，导致的业务不可用时长中，服务调用方承担30%责任，提供方承担70%责任；事故后的改进项中如包含了将强依赖改为弱依赖的改进项，则约定的改造期内（默认1个月）出现同样事故仍按以上比例划分责任。若调用方超期未完成改造，再次出现故障，则服务调用方需平分责任；
  - **服务提供方向服务调用方提出过弱依赖改造需求**，如双方约定的改造期内（默认1个月）出现服务提供方引起的故障，导致的业务不可用时长中，服务调用方承担30%责任，提供方承担70%责任。若故障出现时间已超出约定的改造时间，则服务调用方和服务提供方平分责任；

- 原则：服务间调用应尽量使用弱依赖，降低服务的耦合；

 

d）场景描述：降级后服务存在资损；

- 定责标准：确定服务调用方对服务提供方执行降级恢复稳定性后，导致的额外资金损失由故障主责方或故障触发方负责，且服务调用方和提供方应事先约定好关键预案降级条件；
- 原则：预案明确、资损可控情况下，优先保障服务稳定性，恢复服务正常运行；



- 说明：可降级的标准基于上下游双方事前的约定，降级预案应纳入到上游服务的运行维护中；



**场景2：流量激增过载**

a）场景描述：用户行为或外部原因（网络异常等）导致请求激增引发服务故障；

- 定责标准：异常服务承担故障时长；
- 原则：线上服务对自身需要有容量保护的能力；

- 更详细定责方案参看：http://wiki.intra.xiaojukeji.com/pages/viewpage.action?pageId=36620655
- 说明：服务提供方的故障恢复与否需要由服务提供方明确告知调用方；

**场景3：用户使用平台操作线上服务**

a）场景描述：平台因bug/故障等问题，操作结果非预期，导致线上服务异常或影响止损的及时性；

- 定责标准：从平台引发故障，或平台自身出现异常影响服务止损开始，到服务止损前的时间为平台责任；
- 原则：平台对自身的功能预期和稳定性负责；



b）场景描述：用户事先不了解平台上要操作功能的影响和流程，或操作前没有掌握回滚的方式，导致影响线上服务稳定性或止损的及时性；

- 定责标准：用户全责；

- 原则：用户对自己操作的功能、流程和回滚方式要充分了解；平台的体验问题不能作为用户不事先掌握平台功能、流程和回滚方式的理由，但可以作为优化改进的方向；


**场景4：变更流程**

a）场景描述：非紧急变更（紧急修复线上问题情况除外）服务提供方未提前24小时周知到相关调用方，导致调用方服务异常；

- 定责标准：
  - 调用方无其它失职情况下（报警及时、处理及时），服务提供方全责；
  - 调用方服务未及时报警或处理，服务提供方仍然主责；



b）场景描述：服务提供方提前24小时周知到了相关调用方，或得到调用方的确认后按时进行变更，但变更后调用方服务异常；

- 定责标准：
  - 调用方无其它失职情况下（报警及时、处理及时），服务提供方全责；
  - 调用方服务未检查出异常，或未及时报警并处理，调用方主责；



c）场景描述：线上变更过程中存在其它不符合五条军规要求的情况（变更步骤中未提前准备回滚预案、未遵守分级发布原则、未避开高峰期、未严格检查）；

- 定责标准：存在不符合军规要求的责任方应负主要责任；



- 原则：严格遵守『[线上变更五条军规](http://wiki.intra.xiaojukeji.com/pages/viewpage.action?pageId=100721847)』；
- 通报相关说明：
  - 服务提供方的变更涉及接口变更、增/减接口数据字段、修改接口字段类型、字段值从空到有（待定）均需要在变更前提前通报；
  - 通报内容需明确描述变更点及影响；
  - 提前24小时将变更通报发布到调用方，此类变更无需得到回复到时间可直接变更， 服务调用方自身应尽到及时查阅相应邮件、钉钉消息的义务；
  - 通报未能提前24小时发出的变更，需要得到调用方的确认；
  - 通报方式邮件、钉钉或其它服务方和调用方约定的方式均可；



**场景5：监控**

a）场景描述：用户变更检查时，监控系统自身异常，报警未按预期发出（如BI报警或Odin报警未发出）；

- 定责标准：
  - 用户无法确定服务是否异常，暂停了变更，但故障持续，该情况监控平台全责；
  - 用户未做其它维度的检查，继续了上线，导致故障持续或扩大，该情况变更用户主责；
- 原则：平台对自己的功能负责；用户需按『[线上变更五条军规](http://wiki.intra.xiaojukeji.com/pages/viewpage.action?pageId=100721847)』要求，对核心服务进行多维度的检查（包括业务日志、服务效果等），不能只依赖监控系统；



b）场景描述：无变更情况下，线上服务出现异常达到报警标准，监控延迟发出；

- 定责标准：
  - 监控的一级报警需在达到报警条件后1min内发出报警，否则在异常被业务感知前的故障时间由监控系统负责；
- 原则：平台对自己的功能负责，常态下的异常发现依赖监控报警；


**场景6：基础设施故障**

a）场景描述：以下场景下服务出现异常

- - 单台服务器/单个容器宕机或响应超时；

- - 单台TOR硬件故障；
- 定责标准：服务自身全责；
- 原则：核心服务在架构和部署上需要具备基本的容错能力；



b）场景描述：以下场景下服务出现异常

- - 机房供应商引发的故障，如电力中断等；
  - 电信运营商引发的故障，如运营商网内专线光纤中断、公网出口中断、电信运营商DNS劫持等；
- 定责标准：
  - 多活服务或可调度流量止损的服务，操作方需在故障*15分钟*内完成流量调度止损，*15分钟*后的时间需扣服务方可用性配额；
  - 单活或该情况无止损手段的服务，作为第三方故障处理，不扣服务上的可用性时长；
- 原则：第三方基础设施故障，上层各方如存在止损手段但未及时操作止损的需要对超预期的时间负责；



**场景7：基础运维**

a）场景描述：非变更情况下的日常报警添加和处理出现如下情况

- - 线上报警未及时处理，最终导致服务大面积异常；
  - 线上服务报警遗漏，异常后未能及时发现，最终导致服务大面积异常；
- 定责标准：报警添加和处理的责任方（SRE or RD）负全责；
- 原则：各方对自己服务报警的完备性、有效性和处理的及时性负责；



**场景8：故障响应**

a）场景描述：线上出现服务异常相关责任方未能及时响应（如未接听到报警电话、电话打不通、不能上网等）

- 定责标准：所耽误的处理时间均由该责任方负责；
- 原则：各团队需安排好值班人员，无特殊安排情况下各模块/平台负责人需随时响应相应异常，7 x 24 小时对线上稳定性负责；

## P3以下建议

P3及以下故障不建议相关方过多关注责任百分比划分，应聚焦于暴露出的问题改进。


1、确定事故因素：

受损业务方牵头梳理事故原因，包括[定责流程机制](http://wiki.intra.xiaojukeji.com/pages/viewpage.action?pageId=1041366614)中的直接原因、间接原因、影响面扩大原因；

2、明确责任干系方：
* 根据故障原因，由受损业务方判断并且明确责任干系方；

3、明确定责结果：
* 若责任干系方为一方，则该责任方全责；
* 若责任干系方为多方，则由受损业务方和所有责任干系方共同判定主责方（主责方责任占比至少为55%），及非主责方的责任分摊比例。



# 常见缩写含义

**服务管理**

1. **SLA（Service Level Agreement，服务水平协议）**：
   - **定义**：SLA 是客户和服务提供商之间正式的服务协议，明确了服务的期望、服务标准和服务水平的详细描述。它通常包括服务的可用性、性能、响应时间和其他具体的指标。
   - **示例**：一个典型的 SLA 可能承诺 99.9% 的服务可用性，每月的停机时间不超过 43 分钟。如果达不到这个标准，服务提供商可能需要提供赔偿或其他形式的补偿。

2. **SLI（Service Level Indicator，服务水平指标）**：
   - **定义**：SLI 是用来测量服务性能的具体指标或度量标准，反映了服务在某一特定方面的表现。SLI 是用来评估服务是否满足 SLO（服务水平目标）的基础数据。
   - **示例**：SLI 可能包括服务响应时间（例如，API 请求的平均响应时间为 200 毫秒）、错误率（例如，每百万次请求中的错误数量）、系统吞吐量（例如，每秒处理的请求数）等。

3. **SLO（Service Level Objective，服务水平目标）**：
   - **定义**：SLO 是在 SLA 中定义的特定服务水平目标，是客户和服务提供商共同同意的期望值。SLO 是具体、可测量的，并且通常会有一个时间范围。
   - **示例**：一个 SLO 可能规定，服务的响应时间应该在 95% 的请求中小于 300 毫秒，或者服务的可用性应该在一个季度内保持在 99.95% 以上。

**总结**：

- **SLA** 是客户和服务提供商之间的正式协议，规定了服务期望和标准。
- **SLI** 是用于测量服务性能的具体指标。
- **SLO** 是 SLA 中规定的具体服务水平目标，通常基于 SLI 来衡量。



**通用**

RTT "Round-Trip Time":指从一个网络节点发送数据包到另一个节点，并接收到该节点的确认响应所需的总时间。

# 软件工程

* 霍夫施塔特定律(Hofstadter's Law)，为什么项目交付总是会延期？

  * "计划需要的时间总是比你估计的长，即使你考虑到霍夫施塔特定律。"

* **康威定律（Conway's Law）**：

  - **内容**：系统的设计反映了其开发团队的组织结构。
  - **来源**：《How Do Committees Invent?》，Melvin Conway，1968年。

  **布鲁克斯定律（Brooks's Law）**：

  - **内容**：向一个已经延迟的项目添加人手只会进一步拖延项目进度。
  - **来源**：《The Mythical Man-Month》，Frederick P. Brooks，1975年。

  **莫非定律（Murphy's Law）**：

  - **内容**：凡事只要有可能出错，那就一定会出错。
  - **来源**：这个定律没有明确的单一来源，是一种广为流传的谚语。

  **摩尔定律（Moore's Law）**：

  - **内容**：大约每两年，集成电路上的晶体管数量会翻一番。
  - **来源**：Gordon Moore，1965年。

  **林奇定律（Lynch's Law）**：

  - **内容**：如果你没有时间去做这件事，那你什么时候会有时间去重做它呢？
  - **来源**：常用于项目管理中的谚语，强调第一次把事情做好。
